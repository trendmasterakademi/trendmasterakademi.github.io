The payment provider shows a successful payment, but in WooCommerce the order stays 'Pending payment' or 'On hold'. The order is not fulfilled and may cancel itself after a while. The problem is usually in the step where the payment result is written to the order.

Urgency: Critical · commercial loss · Category: Orders & Payments

Field Observations

The customer says they have paid, and the iyzico or PayTR panel shows a successful transaction. In WooCommerce › Orders, the same order sits with the 'Pending payment' or 'On hold' label. Depending on stock settings, a 'Pending payment' order is cancelled after a while and its stock released.

What you see on screen

Pending payment

WooCommerce order status — official definition: order received, no payment made

On hold

WooCommerce order status — official definition: awaiting payment confirmation, stock reduced

Observed System Error Signatures

  • Provider panel: payment successful · WooCommerce: 'Pending payment' → A · Notification blocked
  • Access log: 403 / 503 on the notification URL ending in ?wc-api= → A · Notification blocked
  • Payment plugin error in the fatal-errors log → B · Plugin error
  • Order note: status set to 'On hold' by the plugin → C · Put on hold on purpose

WooCommerce writes every status change to the order notes. The notes show at a glance whether the status never changed or a plugin changed it on purpose.

Three Potential Root Causes & Differential Tests

A · Notification blocked

The URL where the payment provider reports the result is blocked by a security plugin, a firewall or maintenance mode. In WooCommerce, payment plugins' notification URLs usually end in ?wc-api=. The notification never reaches the order, so the status never changes.

Differential test: Does the callback URL return 403 / 503?

Evidence: 403 / 503 on the notification URL → A

Resolution: Exempt the URL from the firewall

Common anti-pattern fix: Orders are confirmed by hand every day from the provider panel; the block stays in place, so on busy days missed orders cancel themselves.

B · Plugin error

The URL is reachable, but the payment plugin fails while handling the notification: a PHP error, a signature that fails verification, or an amount or order-number mismatch. WooCommerce writes such fatal errors to the fatal-errors log; the order stays unchanged.

Differential test: Is the payment plugin in the fatal-errors log?

Evidence: Plugin error in fatal-errors log → B

Resolution: Fix the error, reprocess the notification

Common anti-pattern fix: The plugin is updated or rolled back without reading the error log; if the cause is a signature or amount mismatch, changing versions does not fix it.

C · Put on hold on purpose

By WooCommerce's definition, 'On hold' means payment confirmation is awaited: stock has been reduced but the payment is not yet confirmed. Some payment methods and plugin settings put orders into this status on purpose. In that case the issue is the approval process, not the code.

Differential test: Do order notes show the plugin set the status?

Evidence: Status changed by the plugin → C

Resolution: Clarify the approval step

Common anti-pattern fix: The plugin setting is changed blindly and orders are confirmed directly; orders get fulfilled before the payment is actually verified.

Check it yourself in the first 10 minutes

  1. Open the affected order's notes: did the status never change, or did a plugin change it?
  2. Find the payment record and the notification attempts for the same order in the payment provider's panel.
  3. In the server access logs, check the requests to the notification URL (in most plugins, the URL ending in ?wc-api=) and the status codes returned.
  4. In WooCommerce › Status › Logs, check the fatal-errors log and the payment plugin's own log.
  5. Check whether a security plugin, a firewall rule or maintenance mode changed in the last few days.

When to hand it over

Hand it over if plugin code or a security rule has to change on the live site, if paid orders in 'Pending payment' must be matched in bulk, or if orders have started cancelling themselves.

Who resolves it

A backend engineer who knows WordPress and the payment plugin. The notification URL must get through the security layers, the plugin error must be found in the logs and fixed, and paid orders stuck in 'Pending payment' must be matched to the provider's records.

Impact If Left Unresolved

When the configured time runs out, WooCommerce cancels 'Pending payment' orders on its own and releases their stock. A paid order is silently cancelled this way; while the customer waits for their product, the stock is sold to someone else.
