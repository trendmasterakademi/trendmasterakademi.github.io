The last unit was sold on the same day on both Trendyol and Hepsiburada, or on both a marketplace and the site. One of the orders has to be cancelled. Stock dropped in one channel but never reached the other channel, or reached it late.

Urgency: Critical · revenue loss · Category: Orders & Payments

Field Observations

Orders for the same item arrive from two channels, and there is one unit in the warehouse. The central stock system shows zero, but the marketplace panel still shows the item in stock. It usually appears on campaign days and right after a bulk stock update.

What you see on screen

status: FAILED · failureReasons: […]

Trendyol batch result check — the request was accepted but the item was not updated

ListingFrozen

Hepsiburada — a locked listing cannot be updated

MismatchingSkusSpecified

Hepsiburada — HBSku and MerchantSku are mismatched

Observed System Error Signatures

  • Batch result: status FAILED on the item row → A · Assumed sent, actually rejected
  • Stock update response is only an operation ID, the result was never queried → A · Assumed sent, actually rejected
  • Stock on the other channel dropped minutes after the order → B · Update arrived late
  • The marketplace order is not in the central stock system → C · Order or item not matched

Marketplaces process stock updates in a queue, not immediately; when the request is accepted, only an operation ID comes back. The real result is in the status check queried with that ID.

Three Potential Root Causes & Differential Tests

A · Assumed sent, actually rejected

When a Trendyol stock and price request is accepted, only a batchRequestId comes back; the per-item result is read from the batch result service, and individual items can fail. Hepsiburada also returns an operation ID (Inventory Upload Id); row-level errors appear in a separate status service. If the result is never queried, the rejected update goes unnoticed.

Differential test: Any FAILED rows in the batch result?

Evidence: FAILED rows in the batch result → A

Resolution: Check results, fix the rejects

Common anti-pattern fix: The same stock request is resent immediately; according to Trendyol's documentation the same request cannot be sent repeatedly for 15 minutes, so the retry is rejected too.

B · Update arrived late

Stock sync runs at intervals or from a queue. When the rate limit fills up, or when Hepsiburada's limit of at most five pending operations at a time is reached, the queue backs up. In the time between the order and the stock drop on the other channel, the last unit can be sold on both channels.

Differential test: Minutes between order and stock drop?

Evidence: Minutes between order and stock drop → B

Resolution: Reserve at order, then push to channels

Common anti-pattern fix: The sync frequency is increased; the request count fills the rate limit faster, and the delay grows instead of shrinking.

C · Order or item not matched

The marketplace order was never pulled into the central system, or the item is matched to the wrong record. An order skipped because of order pull limits, pagination or the query window does not reduce stock. On Hepsiburada, when HBSku and MerchantSku are mismatched, the update is rejected with MismatchingSkusSpecified.

Differential test: Order on the marketplace but not in center?

Evidence: Order on the marketplace, not in the center → C

Resolution: Fix order pulls and item mapping

Common anti-pattern fix: The missing order is entered by hand, but the order pull logic is not fixed; on the next busy day, skipped orders pile up again.

Check it yourself in the first 10 minutes

  1. For the double-sold item, compare the times of the two orders with the moment stock dropped in the central system.
  2. Query the results of the stock updates made around those times: the batch result check on Trendyol, the listing update status check on Hepsiburada.
  3. If the result has FAILED or error rows, note the reason (failureReasons, error name).
  4. Count the marketplace orders of the last few days and check that all of them reached the central system.
  5. Check whether the item's marketplace identifiers (barcode, HBSku, MerchantSku) match the record in the central system.

When to hand it over

Hand it over if the stock reduction logic or the sync queue has to change, if past double sales and stock gaps must be fixed in bulk, or if item mapping must be rebuilt in bulk.

Who resolves it

A backend engineer who knows marketplace integrations. Stock must be reduced in one central place at order time and pushed to the channels from there; the result of every update must be checked, and order pulls must resume from where they stopped.

Impact If Left Unresolved

Every double sale means an order to cancel and a disappointed customer. On campaign days, as the order rate goes up, so does the number of double sales of the same item.
