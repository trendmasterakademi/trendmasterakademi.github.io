An outage occurred, a rollback to backup was requested, only to discover snapshots were never generated or are un-restorable. A backup file existing versus being restorable are entirely different; the latter is unknown until tested.

Urgency: Critical · data loss risk · Category: Handover & Continuity

Field Observations

After database corruption or a server crash, administrators confidently open automated backup archives. Only then do they discover zero-byte files, corrupt tarballs, or dumps dating back six months; panic ensues.

Observed System Error Signatures

  • Last backup file timestamp in directory <- months outdated?
  • cron log: backup job — exit status 1 → A · Backups not running
  • Backup archive size 0 bytes / empty archive
  • Storage provider: quota exceeded → A · Backups not running

Backup routines fail silently most of the time. Errors are emitted to unmonitored logs while stale files in the folder give a false sense of security.

Three Potential Root Causes & Differential Tests

A · Backups not running

Cron was configured but terminated: scheduler daemon died, auth expired, or target bucket filled up.

Differential test: How old is the latest backup file in storage?

Evidence: Latest backup date is stale → A

Resolution: Cron repair + dead-man switch alerts

Common anti-pattern fix: Adding fresh mysqldump cron jobs proves meaningless without automated test restores into staging to verify dump integrity.

B · Partial / incomplete dump

Uploaded assets exist without SQL dumps, or vice versa. Partial snapshots prevent full recovery during disaster recovery.

Differential test: Does archive contain valid SQL dump file?

Evidence: Missing SQL dump in archive → B

Resolution: Full scope dump + file size threshold check

Common anti-pattern fix: Storing dumps in local /backup directories guarantees total data loss when underlying disks fail or hypervisor instances terminate.

C · Un-restorable / corrupted

Archive is corrupt, decryption key is missing, or schema versions clash. Never tested until live disaster hit.

Differential test: Was restore tested in clean sandbox env?

Evidence: Test sandbox restore failed → C

Resolution: Automated drill restoration in staging sandbox

Common anti-pattern fix: Taking database dumps without single-transaction flags produces fractured relational states that fail integrity checks during emergency recovery imports.

Resolution Path & Time to Fix

Sysadmin / DevOps. But the true solution is procedural: dead-man failure alerts and scheduled sandbox restoration drills. An untested backup is not a backup.

Impact If Left Unresolved

Every day operating without restorable backups is a single disk crash or rogue query away from total business termination.
