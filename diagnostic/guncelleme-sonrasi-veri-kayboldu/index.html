Records vanish after a release, triggering data deletion panic. In most incidents, data remains intact; the query reading it mutated. Attempting hasty fixes without proper diagnosis risks causing genuine data loss.

Urgency: Critical · data panic · Category: Data & Migration

Field Observations

Following a late-night release, store managers discover that recent orders, customer notes, or custom attributes vanished. Customer support calls asking 'Where is my order?' provide the first concrete evidence of lost data.

Observed System Error Signatures

  • Migration logs: rolled back or interrupted mid-execution → B · Interrupted schema migration
  • Column not found / Unknown column in field list → B · Interrupted schema migration
  • Row count: does table row count still match previous value?
  • Were status or soft-delete flags updated in bulk?

The first step is counting table rows directly. If row counts match, data is not erased; its visibility is filtered out. This distinction fundamentally changes the incident response vector.

Three Potential Root Causes & Differential Tests

A · Default query filter changed

A new status column or soft-delete flag was added; legacy rows fail the default WHERE clause.

Differential test: Is database row count identical to baseline?

Evidence: Row count unchanged in DB → A

Resolution: Backfill default flag on legacy records

Common anti-pattern fix: Restoring a full database backup wipes out all legitimate new orders created between the migration event and the recovery attempt.

B · Interrupted schema migration

DDL migration halted mid-stream; half the tables are upgraded, causing joins to fail.

Differential test: Did migration log terminate with an unhandled error?

Evidence: Migration abort in deploy log → B

Resolution: Restore snapshot · re-run clean migration script

Common anti-pattern fix: Fixing database credentials in .env re-points future traffic, but legitimate customer records already written into staging remain abandoned and unmerged.

C · Genuine bulk deletion

A runaway script or bad WHERE clause executed actual hard DELETE. Rare, but the only true data loss scenario.

Differential test: Did physical row count actually drop?

Evidence: Row count decreased in DB → C

Resolution: Point-in-time backup restore · time critical

Common anti-pattern fix: Running Redis flushall purges volatile caches alongside unpersisted cart sessions sharing the same instance, destroying customer state irreversibly.

Resolution Path & Time to Fix

The absolute first rule is freezing all writes. Writing new data or altering schemas destroys recovery options. A is resolved in minutes, B via atomic rollback, C requires immediate point-in-time snapshot recovery.

Impact If Left Unresolved

Under true deletion, the recovery window equals snapshot retention. The most frequent catastrophe is attempting blind repairs that overwrite restorable blocks.
