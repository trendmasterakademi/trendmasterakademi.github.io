The application slows down or freezes predictably every afternoon; rebooting restores normal function. Daily reboots are not a solution but a temporary band-aid — with degradation creeping earlier every day.

Urgency: High · masked defect · Category: Infrastructure & Access

Field Observations

The system bogs down daily at similar hours and relies on a nightly cron reboot to stay alive. Customers notice snappy mornings but sluggish checkout afternoons; the failure has become routine yet remains unresolved.

Observed System Error Signatures

  • Out of memory: Killed process
  • Memory consumption climbs steadily without dropping
  • Process manager (PM2): daily restart count increasing
  • Response latencies degrade progressively during peak hours

Memory utilization graphs provide instant diagnosis: sawtooth patterns reflect healthy garbage collection; monotonic linear ascent proves memory leaks.

Three Potential Root Causes & Differential Tests

A · Application memory leak

Unbounded caches or unclosed references accumulate until Linux OOM killer terminates the process.

Differential test: Does RAM graph ever drop during idle periods?

Evidence: RAM usage never drops → A

Resolution: Heap dump profile + patch leak

Common anti-pattern fix: Scheduling twice-daily reboots fails because leaky code cycles continue exhausting RAM during sudden mid-day traffic surges.

B · Unbuffered export spike

Bulk CSV export loads entire 500k row database into memory buffer at once, triggering instant OOM.

Differential test: Do memory spikes correlate with bulk export jobs?

Evidence: Crash coincides with heavy report → B

Resolution: Stream chunking + generator buffer

Common anti-pattern fix: Manually purging temp directories with rm -rf fails because missing logrotate configurations allow multi-gigabyte log dumps to exhaust disk space again.

C · Genuine capacity ceiling

Zero memory leaks; active concurrent user count simply exceeded instance memory limits.

Differential test: Is RAM steady high proportional to active users?

Evidence: Stable high load proportional to traffic → C

Resolution: Scale instance RAM · valid upgrade

Common anti-pattern fix: Indiscriminately terminating tasks with killall -9 leaves orphaned database sockets hanging, locking connection pools on the very next cycle.

Resolution Path & Time to Fix

A and B are application bugs; automated cron reboots mask them without fixing. C is legitimate hardware scaling — but upgrading before diagnosing A & B wastes cloud spend while crashes persist.

Impact If Left Unresolved

Daily reboots inevitably degrade into multi-hour crashes during high-traffic campaign peaks. It is a scheduled disaster waiting to execute.
