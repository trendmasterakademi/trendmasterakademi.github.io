Orders complete, but e-Archive invoices are not created, are created incomplete, or are rejected by the integrator. The invoice drops at one link of the chain from the order to the integrator; the integrator's response and the order record together tell you which link.

Urgency: High · legal obligation · Category: Orders & Payments

Field Observations

The customer says the invoice never arrived by email, or the accountant notices at month end that orders and invoices do not match. The order looks 'completed' on the site, while the integrator's panel has no invoice for it or shows it as 'rejected'.

What you see on screen

Integrator panel: no invoice · or 'rejected'

The private integrator's panel — error codes and messages differ by integrator

Observed System Error Signatures

  • Integrator panel: no invoice record for the order number → A · Connection broken
  • Application log: integrator request 401 or timeout → A · Connection broken
  • Integrator response: rejected · buyer tax ID / national ID or address invalid → B · Integrator rejected it
  • Buyer's tax ID is a registered e-Invoice user, invoice sent as e-Archive → C · Wrong invoice type

The integrator issues the invoice and transmits it to the Turkish Revenue Administration; the site's job is to send the right data once and log the response. If the integrator's rejection is not logged, the problem stays invisible.

Three Potential Root Causes & Differential Tests

A · Connection broken

The request from the site to the integrator never leaves or drops on the way: credentials changed, the access token expired, the integrator's address changed, or the request times out. The integrator's panel has no record at all for that order.

Differential test: Does the integrator have a record for the order?

Evidence: No record at the integrator, 401 in the app → A

Resolution: Fix credentials, queue the requests

Common anti-pattern fix: Orders without invoices are invoiced one by one by hand in the integrator's panel, but the connection is not fixed; the next day the same list forms again.

B · Integrator rejected it

The request reaches the integrator but is rejected because the invoice data is missing or wrong: the buyer's tax ID or national ID number, address, tax rate or amount fields. If the rejection is not logged, the site assumes the invoice was issued.

Differential test: Is there a rejection in the response?

Evidence: Rejection and error code in the response → B

Resolution: Fix the data, send it once

Common anti-pattern fix: The rejected invoice is resent with the same data; since the data is not fixed it is rejected again, or two invoices get created for the same order during the fix.

C · Wrong invoice type

According to the Turkish Revenue Administration, the e-Archive invoice is issued for sales to taxpayers not registered in the e-Invoice system and to non-taxpayers. If the buyer is registered in the e-Invoice system, the invoice must be issued as an e-Invoice. If the site sends an e-Archive invoice without checking whether a business buyer is registered, the invoice is issued as the wrong type or rejected by the integrator.

Differential test: Is the buyer registered for e-Invoice?

Evidence: Buyer registered for e-Invoice, e-Archive sent → C

Resolution: Choose the type per buyer

Common anti-pattern fix: The invoice type is left hard-coded and only the rejected orders are fixed by hand; every new order from a business buyer repeats the same case.

Check it yourself in the first 10 minutes

  1. List the latest invoices in the integrator's panel and compare them with orders to find which orders have no invoice.
  2. For orders without invoices, look for the request sent to the integrator and the response in the application logs: no request means the connection, a rejection means the data.
  3. Look the error code in rejections up in the integrator's own documentation.
  4. For business buyers with a tax ID, check whether the buyer is on the Turkish Revenue Administration's list of registered e-Invoice users.
  5. Check whether the integrator user credentials or access key changed recently, or whether the contract or usage allowance ran out.

When to hand it over

Hand it over if the code that creates invoices has to change, if orders left without invoices must be invoiced in bulk, or if a decision about invoice type and tax fields is needed. Tax and regulatory decisions belong to the accountant; the technical team only fixes the connection.

Resolution Path & Time to Fix

A backend engineer who knows the integration, together with the accountant. The engineer fixes the connection, the logging of rejections and the one-time resubmission of missing invoices; decisions about invoice type and tax fields belong to the accountant.

Impact If Left Unresolved

When invoices for goods sold are not issued on time, the problem stops being technical and becomes a legal obligation. As orders without invoices pile up, so does the explaining owed to customers and to the accountant.
