The PayTR payment frame will not open, or the customer pays but the transaction stays 'In Progress' in the PayTR panel. There are two separate breaks: in the token request before payment, or at the notification URL after payment. PayTR's own response tells you which.

Urgency: Critical · checkout halted · Category: Orders & Payments

Field Observations

Instead of the payment frame, the checkout page shows an empty area or an error message. Or the payment goes through and the customer receives the bank's confirmation, but the order is never confirmed on the site. On the Transactions page of the PayTR merchant panel, the same payment waits as 'In Progress'.

What you see on screen

Transactions › In Progress

PayTR merchant panel — payment taken, no 'OK' reply to the notification

get-token response: status ≠ success · reason: …

Token request response — the payment frame never opens

Observed System Error Signatures

  • get-token response: status is not success, reason field is filled → A · Token request rejected
  • Transactions page: payment taken, status 'In Progress' → B · No 'OK' to the notification
  • Notification URL access log: the same merchant_oid arrives every minute → B · No 'OK' to the notification
  • Stock reduced twice and two confirmation emails for one merchant_oid → C · Notification processed twice

With debug_on=1 added to the token request during integration, PayTR spells out the cause of the error. Either way, the cause is in the reason field of the response; look there first.

Three Potential Root Causes & Differential Tests

A · Token request rejected

The get-token request made before payment fails. The most common cause is a paytr_token signature not built in the documented order: field order, the amount not multiplied by 100, the basket not base64-encoded, or test_mode left out of the signature.

Differential test: Does get-token return a filled reason field?

Evidence: reason field filled in the response → A

Resolution: Fix signature order and amount

Common anti-pattern fix: debug_on is switched off so the error disappears from view; the payment frame still does not open, but now the cause is hidden too.

B · No 'OK' to the notification

The payment was taken and PayTR sent the result to the notification URL, but the reply is not the plain text 'OK'. According to PayTR's documentation the notification then counts as failed, is retried a minute later, and the transaction stays 'In Progress' in the panel. An HTML page, an error page or a redirect also means PayTR did not get 'OK'.

Differential test: Is the same notification sent every minute?

Evidence: Same notification arrives every minute → B

Resolution: Reply with plain text 'OK' only

Common anti-pattern fix: Orders are confirmed by hand from the PayTR panel; since the notification URL is never fixed, the same chore repeats with every payment and missed orders are never fulfilled.

C · Notification processed twice

PayTR may send more than one notification for the same payment. The documentation says only the first should be acted on and repeats should simply get 'OK'. Without this check the same order is confirmed twice: stock drops twice and the customer gets two emails.

Differential test: Was the same merchant_oid processed twice?

Evidence: Same merchant_oid processed twice → C

Resolution: Act on the first, 'OK' the repeats

Common anti-pattern fix: To block repeats, the notification URL returns an error to the second notification; PayTR counts that as a failed notification and keeps retrying.

Check it yourself in the first 10 minutes

  1. In the PayTR merchant panel, check the status of the affected payment on the Transactions page. 'In Progress' means the payment was taken and the notification was never completed.
  2. If the payment frame does not open, repeat the token request in your integration environment with debug_on=1 and read the reason field of the response.
  3. Check that the notification URL points to the right address and does not redirect.
  4. In the server access logs, look at requests to the notification URL and the replies sent. If the same merchant_oid arrives every minute, the reply is not 'OK'.
  5. Check orders for two records, two stock reductions or two confirmation emails with the same merchant_oid.

When to hand it over

Hand it over if the signature calculation or the notification reply has to change in code, or if 'In Progress' payments must be matched to orders in bulk. Trial and error in live payment code creates new duplicate transactions.

Who resolves it

A backend engineer who knows payment integrations. The lasting fix has three parts: building the signature in the documented order, a notification URL that verifies the incoming hash and replies with plain 'OK' only, and never processing the same merchant_oid twice.

Impact If Left Unresolved

Every 'In Progress' transaction is a customer who has paid but whose order was never confirmed. If the break is on the token side, payment never starts; the cart is abandoned and the loss shows up in no panel at all.
