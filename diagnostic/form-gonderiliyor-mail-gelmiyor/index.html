Lead or quote forms display 'Submitted successfully' but notifications never arrive in the team inbox. The most insidious defect: silence leaves lost deals completely untracked.

Urgency: High · lost leads · Category: Contact & Integrations

Field Observations

Visitors submit quote forms and receive a cheerful 'Message sent successfully' banner. Yet nothing arrives in corporate inboxes. The failure operates in total silence; how many high-value leads were lost only becomes apparent weeks later.

Observed System Error Signatures

  • SMTP error 535 Authentication failed → A · SMTP auth failure
  • 550 5.7.1 Message rejected · SPF / DKIM → B · Missing SPF / DKIM
  • Mail queue: deferred / stuck → B · Missing SPF / DKIM
  • App logs: 'mail sent' <- but never delivered by MTA

'Message sent' in UI only reflects dispatch, not inbox delivery. Truth resides in server mail queues (Postfix/Exim) or transactional ESP dashboards (SendGrid/Postmark).

Three Potential Root Causes & Differential Tests

A · SMTP auth failure

Mailbox password expired or ESP enforced App Passwords/OAuth. Dispatch fails at origin.

Differential test: Is there an SMTP 535 auth error in system logs?

Evidence: SMTP 535 Authentication failed in log → A

Resolution: App Password + config update in .env

Common anti-pattern fix: Reverting to native PHP mail() dispatches unauthenticated envelopes that destination mail exchangers quietly quarantine or drop entirely.

B · Missing SPF / DKIM

Mail leaves server but destination MX rejects or junk-folders it due to missing SPF/DKIM/DMARC TXT records.

Differential test: Are SPF and DKIM TXT records active in DNS?

Evidence: 550 5.7.1 SPF/DKIM rejected → B

Resolution: Add DNS records · deliverability restored

Common anti-pattern fix: Injecting the submitter's email into the RFC-5322 From header triggers DMARC alignment failures, causing destination servers to reject delivery.

C · False positive frontend

AJAX endpoint returns 4xx/5xx but frontend ignores HTTP status and shows optimistic success alert.

Differential test: Does network tab show HTTP 200 on POST request?

Evidence: Network tab shows 4xx/5xx → C

Resolution: Handle status · render error UI on failure

Common anti-pattern fix: Masking frontend errors without checking server logs maintains a false sense of success while API endpoints continue throwing 500 exceptions.

Who resolves it

A and B are DNS/Sysadmin issues. C is frontend defect that must be solved first: false-positive success toasts hide lead bleed for months.

Impact If Left Unresolved

Every lost form is a lost deal that nobody knows was missed. This defect never announces itself; it bleeds revenue in silence.
