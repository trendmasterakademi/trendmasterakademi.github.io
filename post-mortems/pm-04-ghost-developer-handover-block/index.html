Incident Summary

The sole lead engineer departed abruptly. Production environment secrets were missing from Git, the primary AWS root was bound to the developer’s personal email, and the CI/CD pipeline depended on private uncommitted runner scripts.

Business & Technical Impact

Zero deployments possible for 3 weeks; production hotfixes stalled; critical security exposure from active ex-developer keys.

Incident Timeline

  • T+00h · Crisis Escalation: Project Paralysis — Agency attempted a critical client bugfix; discovered production credentials were missing and deploys failed.
  • T+06h · TMA Forensic Extraction — Extracted active production secrets and database passwords directly from running Linux process memory (/proc/$PID/environ).
  • T+18h · AWS Ownership & DNS Verification — Leveraged DNS ownership to establish organizational authority with AWS Support; provisioned clean IAM root.
  • T+36h · Pipeline Reconstructed (GitHub Actions) — Decommissioned untrusted external runner; built self-contained, documented GitHub Actions CI/CD workflows.
  • T+48h · First Clean Deploy & Full Agency Ownership — Revoked all legacy credentials; agency executed its first verified, autonomous deployment to production.

Root Cause Analysis (5 Whys)

1. Production secrets stored exclusively on a personal machine without a central vault. 2. Cloud infrastructure registered under an individual employee email rather than corporate identity. 3. Bus factor of 1 with zero architectural documentation.

TMA SWAT Resolution & Hotfix

1. Extracted and validated live environment secrets from process memory into an encrypted vault. 2. Revoked all existing SSH keys, API tokens, and IAM credentials tied to the ex-developer. 3. Built a standardized, single-click GitHub Actions deployment pipeline.

Permanent Mitigations

• Codified the TMA 12-Point Handover Audit as a mandatory contractual requirement for all contractors. • Enforced centralized secret management via AWS Secrets Manager with automated rotation.
